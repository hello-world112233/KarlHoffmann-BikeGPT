# 系统说明文档：场地自行车 AI 数据与模型闭环

## 1. 系统目标

本系统的核心目标不是简单地“分类视频”或“生成分析报告”，而是建立一个能让模型逐步理解场地自行车场景中“人-车-动作关系”的数据与分析系统。

更具体地说，本系统希望做到：

1. 将固定座视频、真实训练视频、比赛全程视频等不同来源的数据统一管理。
2. 从全程视频中提取出真正有价值的动作片段，例如出发、加速、冲刺、弯道、遮挡和多人干扰片段。
3. 用 Sapiens2、RTMPose 等通用模型建立 baseline，发现它们在自行车场景中的失效模式。
4. 将失败片段沉淀为 hard cases，用于标注、微调、约束建模和后续模型评估。
5. 逐步建设自行车专项姿态数据集，使模型更好地理解“人骑在场地自行车上”这一强物理约束场景。
6. 最终将高可信姿态识别和运动指标转化为教练、运动员和科研人员可用的复盘材料。

系统的长期闭环是：

```text
真实数据采集
  -> 数据入库与分类
  -> 自动事件索引与切片
  -> baseline 姿态识别
  -> 失败样本挖掘
  -> 人工标注与专项数据集
  -> 模型改进与评估
  -> 教练复盘与科研输出
  -> 指导下一轮采集
```

## 2. 为什么需要清晰的数据分类

如果只把所有视频混在一起，系统会很快变得混乱：

- 固定座视频和比赛视频的难度不同，不能混为一谈。
- 比赛全程视频中包含多个动作阶段，不能直接当成一个训练样本。
- 清晰侧面视频和远景遮挡视频的用途不同，不能用同一标准处理。
- 有些视频适合训练，有些适合验证，有些只适合做 hard case。

因此，本系统采用三层分类法：

```text
来源域 Domain
  -> 动作/事件 Event
  -> 视角与质量 View & Quality
```

这三层不是为了整理文件夹而整理文件夹，而是为了回答几个核心问题：

1. 这个数据来自哪里？
2. 视频里发生了什么动作？
3. 这个样本对模型来说难在哪里？
4. 它适合用于训练、验证、失败分析，还是教练复盘？

## 3. 第一层：来源域 Domain

来源域回答的问题是：

> 这个视频来自什么环境？

这是最基础的分类，用来决定数据可靠性、应用边界和后续用途。

| Domain | 含义 | 主要用途 | 注意事项 |
|---|---|---|---|
| `trainer_static` | 固定座/训练架视频 | 干净 baseline、标注练习、踏蹬周期分析、系统调试 | 动作不完全等同真实场地骑行 |
| `field_training` | 真实训练视频 | 目标场景数据、教练复盘、模型验证 | 最重要的数据来源 |
| `competition_full` | 比赛全程视频 | 原始比赛素材，先做事件索引 | 不建议整段直接跑模型 |
| `competition_clip` | 从比赛全程中切出的片段 | baseline、hard case、真实难场景测试 | 需要有事件标签 |
| `lab_controlled` | 实验室/标定视频 | 3D、多机位标定、几何约束验证 | 可用于精度基准 |
| `unknown` | 尚未整理的数据 | 临时存放 | 必须后续人工或自动分类 |

### 当前已有数据

目前项目已有：

```text
competition_full
trainer_static
```

其中比赛全程视频已经上传到 AutoDL，并完成了第一轮视频盘点。

## 4. 第二层：动作/事件 Event

动作/事件回答的问题是：

> 这个片段里发生了什么动作？

它是模型训练、姿态分析和教练复盘最关心的层级。

| Event | 含义 | 主要价值 |
|---|---|---|
| `standing_start` / `start` | 原地出发或比赛开端 | 出发阶段姿态识别、第一蹬、启动表现 |
| `rolling_start` | 行进间启动 | 加速节奏、踏频爬升 |
| `first_lap_acceleration` | 第一圈加速 | 出发后持续加速能力 |
| `steady_pedaling` | 匀速踏蹬 | 踏蹬周期、左右相位、稳定性 |
| `sprint` | 冲刺/高速段 | 高速模糊、姿态稳定性、爆发动作 |
| `curve` | 弯道 | 车身倾斜、视角变化、遮挡 |
| `straight` | 直道 | 姿态较稳定，适合基线分析 |
| `aero_position` | 低姿态/俯冲 | 躯干角度、空气动力姿态 |
| `occlusion` | 遮挡片段 | hard case，测试遮挡鲁棒性 |
| `multi_rider` | 多人/多车 | 测试选错人、多目标干扰 |
| `far_view` | 远景 | 测试低分辨率和比赛视角 |
| `hard_case` | 模型困难样本 | 用于评估和模型改进 |
| `other` | 其他 | 临时兜底 |

### 比赛全程视频的处理原则

比赛全程视频本身不直接作为一个 `event`。

正确流程是：

```text
competition_full
  -> 自动事件候选
  -> 切片
  -> competition_clip + event label
```

例如：

```text
competition_full_personal_男子1km计时赛_吕杰
  -> start clip
  -> sprint clip
  -> hard_case clip
```

## 5. 第三层：视角与质量 View & Quality

视角与质量回答的问题是：

> 这个样本对模型来说难在哪里？

### View 视角

| View | 含义 | 价值 |
|---|---|---|
| `side` | 侧面 | 髋-膝-踝、踏蹬周期最清楚 |
| `front` | 正前 | 左右对称、车身摆动 |
| `rear` | 正后 | 后方视角、左右稳定性 |
| `front_oblique` | 前斜侧 | 真实训练/比赛常见视角 |
| `rear_oblique` | 后斜侧 | 遮挡和真实观察视角 |
| `high_view` | 高位视角 | 看台/俯视场景 |
| `far_view` | 远景 | 比赛视频常见，模型较难 |
| `closeup_lower` | 下肢近景 | 脚踝、踏板、膝盖细节 |
| `unknown` | 未知 | 需要后续整理 |

### Quality 质量/难度标签

| Quality | 含义 | 用途 |
|---|---|---|
| `high_quality` | 清晰、无遮挡、主体较大 | 训练和标注优先 |
| `motion_blur` | 高速运动模糊 | hard case |
| `low_resolution` | 人体较小或分辨率不足 | 鲁棒性测试 |
| `occlusion` | 车架/对侧腿/他人遮挡 | 自行车场景关键难点 |
| `truncation` | 人或车出画 | 数据质量风险 |
| `lighting_issue` | 光照、反光、阴影问题 | 真实场景挑战 |
| `multi_person_confusion` | 多人导致模型选错 | 比赛/训练常见问题 |
| `camera_motion` | 手持或机位运动 | 可能影响模型稳定性 |
| `unknown` | 未判断 | 临时状态 |

## 6. 一个样本的完整身份

一个视频或片段不应该只有文件名，而应该有完整身份。

示例 1：比赛远景出发片段

```yaml
domain: competition_clip
event: start
view: far_view
quality:
  - low_resolution
  - multi_rider
use: hard_case_validation
```

示例 2：固定座侧面踏蹬

```yaml
domain: trainer_static
event: steady_pedaling
view: side
quality:
  - high_quality
use: clean_baseline_annotation
```

示例 3：真实训练侧面出发

```yaml
domain: field_training
event: standing_start
view: side
quality:
  - high_quality
use: target_domain_training
```

## 7. 不同数据的用途

### 固定座视频 `trainer_static`

固定座视频不是废数据，但它的用途要明确。

适合用于：

- 系统调试
- 姿态模型 baseline
- 标注练习
- 踏蹬周期分析
- 人体点和自行车专项点定义
- 干净场景下模型表现测试

不适合单独用于：

- 证明真实比赛表现
- 替代场地训练数据
- 直接推断出发加速度和真实车身动态

### 比赛全程视频 `competition_full`

比赛全程视频非常有价值，但不适合整段直接跑模型。

适合用于：

- 自动事件候选
- 切出真实困难片段
- 建立 hard case
- 测试模型鲁棒性
- 观察比赛视角下的低分辨率、遮挡和多人问题

处理方式：

```text
competition_full -> event index -> competition_clip
```

### 比赛切片 `competition_clip`

比赛切片是第一轮 baseline 的重要输入。

适合用于：

- Sapiens2 / RTMPose baseline
- 失败样本挖掘
- hard case 标注
- 模型鲁棒性评估

### 真实训练视频 `field_training`

真实训练视频是后续最重要的数据。

适合用于：

- 目标域训练和验证
- 教练复盘
- 运动表现指标分析
- 训练建议生成

## 8. 参数提取应该分阶段

不要一开始对所有视频都提复杂运动指标。

正确顺序是：

```text
阶段 1：数据元信息
阶段 2：事件切片
阶段 3：模型质量评估
阶段 4：运动表现指标
```

### 阶段 1：数据元信息

对所有视频都提：

- 时长
- 帧率
- 分辨率
- 文件大小
- 亮度
- 模糊程度
- 运动强度
- 来源域

### 阶段 2：事件切片

主要针对 `competition_full`：

- start
- sprint
- curve
- occlusion
- hard_case

### 阶段 3：模型质量评估

对切片或抽帧跑 baseline 后提：

- 关键点置信度
- 脚踝/膝盖/髋关节丢失率
- 关键点时序抖动
- 左右腿混淆
- 多人选错
- 遮挡失败

### 阶段 4：运动表现指标

只有当姿态结果足够可信时，再提：

- 踏频
- 左右对称
- 躯干前倾
- 第一蹬节奏
- 出发阶段姿态稳定性
- 加速窗口
- 功率/肌电/心率多模态关系

## 9. 当前项目的近期路线

当前已有 6 个比赛全程视频。近期路线是：

```text
1. 保留 competition_full 原始视频
2. 自动生成事件候选 auto_competition_events.csv
3. 自动切出 competition_clip
4. 对切片跑 baseline
5. 自动或半自动发现 hard cases
6. 根据失败类型决定长兴补采什么
```

不要直接进入复杂 Web，也不要直接训练模型。

第一目标是建立：

```text
已有视频 -> 自动候选切片 -> baseline -> 失败地图
```

## 10. 如何判断是否走偏

每增加一个功能，都问五个问题：

1. 它是否让数据更可复用？
2. 它是否让模型错误更清楚？
3. 它是否让标注更有方向？
4. 它是否能服务教练复盘？
5. 它是否能沉淀成科研证据？

如果都不能，就暂时不要做。

## 11. 一句话总结

本系统不是在整理视频文件，而是在给模型建立一张地图：

```text
哪些场景模型会？
哪些场景模型不会？
我们缺什么数据？
哪些样本适合训练？
哪些样本适合验证？
哪些结果能说服教练、老师和评审？
```

因此，当前最重要的数据组织原则是：

```text
按来源域管理原始视频；
按动作事件管理切片；
按视角和质量管理模型难度。
```
