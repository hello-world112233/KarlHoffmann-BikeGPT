# 项目读图说明：你现在到底拥有了什么

这份文档是给“第一次管理复杂 AI 项目的人”看的。它不假设你已经熟悉大型工程，只解释这个项目为什么这样分、每天怎么用、下一步怎么做。

## 1. 这个项目到底是什么

`bike-ai-platform` 不是一个普通网页，也不是一堆分析脚本。它是一个面向场地自行车训练的长期 AI 项目。

它要做的事情可以压缩成一句话：

> 把真实训练视频变成可积累的数据资产，再用这些数据不断改进自行车姿态识别模型，最后把高可信结果反馈给教练和运动员。

所以它同时包含三件事：

1. 数据系统：采集、登记、抽帧、标注、版本管理。
2. 模型系统：Sapiens2/RTMPose baseline、自行车专项模型、误差评估。
3. 产品系统：教练复盘、报告、历史对比、训练建议。

现在的骨架不是最终产品，而是为了让这三件事以后能长在同一棵树上。

## 2. 为什么不直接写一个网页

因为网页只是外壳。你现在最珍贵的是长兴驻队期间能采到真实数据。如果没有数据规范和模型评估闭环，网页做得再漂亮，也会退化成一次性 demo。

正确顺序是：

```text
数据先变干净 -> 模型先能跑 baseline -> 知道模型哪里错
-> 选 hard cases 标注 -> 改进模型 -> 再做教练复盘产品
```

网页会做，但它应该服务这个闭环。

## 3. 文件夹怎么理解

### `docs/`

这里是你的“大脑”和“项目记忆”。

你应该经常打开这些文件：

- `product_vision.md`：这个产品为什么存在。
- `data_protocol.md`：每条视频要记录哪些信息。
- `annotation_protocol.md`：以后怎么标注人体点和自行车点。
- `model_roadmap.md`：模型从 baseline 到专项模型怎么走。
- `changxing_6day_plan.md`：驻队 6 天该怎么推进。
- `project_walkthrough.md`：也就是本文。

不要小看文档。对科研型项目来说，文档就是你以后写申请书、论文、汇报和交接的底稿。

### `configs/`

这里放配置，不放代码逻辑。

比如：

- 本地 Mac 用哪个数据目录。
- AutoDL 服务器用哪个数据目录。
- Sapiens2 模型在哪里。
- 失败样本有哪些类型。

这样做的好处是：以后换服务器、换模型、换数据目录，不需要到处改代码。

### `src/bike_ai/`

这里是长期可复用的 Python 包。

你可以把它理解成“真正的系统能力”。

- `registry/`：视频登记。每条视频是谁、什么场景、什么机位。
- `ingestion/`：视频导入和抽帧。
- `models/`：模型适配器。Sapiens2、RTMPose、自研模型以后都放这里。
- `inference/`：批量跑模型。
- `annotation/`：导出/导入标注任务。
- `evaluation/`：评估模型，整理失败样本。
- `review/`：未来给教练和科研人员看的复盘视图。
- `common/`：通用工具，比如读取配置、创建目录。

原则：只要是以后会长期复用的能力，就沉淀到 `src/bike_ai/`。

### `scripts/`

这里是“你每天实际敲命令用的入口”。

例如：

```bash
python scripts/register_video.py ...
python scripts/extract_frames.py ...
python scripts/run_baseline.py ...
```

你可以把 `scripts/` 理解成遥控器，把 `src/bike_ai/` 理解成机器内部。

### `data/`

这里放本地数据，但它不进 Git。

真实视频、大量图片、模型输出都很大，也可能涉及运动员隐私，所以不能提交到 GitHub。

### `experiments/`

这里记录每次实验。

比如你跑了一次 Sapiens2 baseline，就建一个实验记录：

```text
experiments/2026-07-15_sapiens2_baseline/
```

里面记录：

- 用了哪些视频
- 用了什么模型
- 输出在哪里
- 错误类型有哪些
- 下一步该补采什么

实验记录以后会变成论文和汇报里的证据。

### `datasets/`

这里记录数据集版本，不放大文件。

例如：

```text
CX-BikePose-v0.1：包含 12 个运动员、4 类场景、500 张关键帧标注。
```

以后你训练模型时，必须知道自己用的是哪个数据集版本。

### `apps/`

这里以后放网页和 API。

现在它不是最优先的。等数据和 baseline 跑起来以后，再做复盘界面更有价值。

## 4. 你每天应该怎么用这个项目

白天采数据，晚上进系统。

每天晚上建议固定做这 5 步：

1. 把当天视频放到数据目录。
2. 用 `register_video.py` 登记每条视频。
3. 用 `extract_frames.py` 抽关键帧。
4. 跑 baseline，生成模型输出和可视化。
5. 记录今天模型哪里错，明天该补采什么。

最重要的是第 5 步，因为它会让采集越来越有方向。

## 5. 接下来怎么一步一步实现

不要想着“一口气做完整平台”。你要按闭环来。

### 第 0 步：熟悉项目

目标：你知道每个文件夹是干什么的。

今天就做到：

- 打开 `README.md`
- 打开 `docs/project_walkthrough.md`
- 打开 `docs/data_protocol.md`
- 打开 `docs/changxing_6day_plan.md`

### 第 1 步：让视频能入库

目标：每条视频都有规范记录。

要完成：

- 确认命名规则。
- 跑通 `register_video.py`。
- 生成 `data/registry/*.json`。

成功标准：

> 你拿到任意一个视频，都能知道它是谁、什么场景、什么机位、什么时候拍的、有没有遮挡、教练备注是什么。

### 第 2 步：让视频能抽帧

目标：把视频变成可检查、可标注的图片。

要完成：

- 跑通 `extract_frames.py`。
- 每条视频按 `video_id` 输出抽帧目录。

成功标准：

> 你能快速浏览关键帧，判断画面质量是否适合训练模型。

### 第 3 步：跑 Sapiens2 baseline

目标：先不训练模型，先知道通用模型在自行车视频里哪里错。

要完成：

- 在 AutoDL 上实现 `Sapiens2PoseModel`。
- 输入图片或视频帧，输出关键点和置信度。
- 保存原始输出和 COCO-17 子集。

成功标准：

> 系统能自动生成一批带关键点的图片，你能肉眼看出哪些帧识别错了。

### 第 4 步：建立失败样本库

目标：把“模型错了”变成可分析资产。

要完成：

- 用 `configs/failure_taxonomy.yaml` 里的类型标记失败帧。
- 每个失败样本记录 `video_id`、`frame_id`、错误类型、严重程度、备注。

成功标准：

> 你能说清楚：Sapiens2 在自行车场景下主要错在哪里。

### 第 5 步：导出标注任务

目标：不是盲目标注，而是优先标注 hard cases。

要完成：

- 从失败样本中选择 200-500 张关键帧。
- 导出给 CVAT 或 Label Studio。
- 标 COCO-17 和必要的自行车专项点。

成功标准：

> 你拥有第一版自行车专项姿态数据集。

### 第 6 步：评估和改进模型

目标：从“用了大模型”变成“证明我们在自行车场景里提升了精度”。

要完成：

- 建立验证集。
- 对比 Sapiens2、RTMPose、约束修正版、自研模型。
- 输出 PCK、关键点误差、失败类型减少情况。

成功标准：

> 你能用实验结果证明：自行车专项数据和约束确实提高了姿态识别精度。

### 第 7 步：做教练复盘产品

目标：把模型能力翻译成教练能用的语言。

要完成：

- 视频 overlay
- 关键帧
- 动作阶段
- 左右对称
- 出发节奏
- 与历史样本对比
- 报告输出

成功标准：

> 教练看完能知道下一次训练该注意什么。

## 6. 你现在最应该做什么

现在不要先做大而全的 Web。

你接下来最应该做：

1. 拿一个真实视频。
2. 跑通视频登记。
3. 跑通抽帧。
4. 把抽出的帧带到 AutoDL 上准备跑 Sapiens2。
5. 写下第一批模型失败观察。

这就是第一条真正的闭环。

## 7. 怎么判断自己没有走偏

每做一个功能，都问：

1. 它是否让数据更可复用？
2. 它是否让模型误差更清楚？
3. 它是否让标注更有方向？
4. 它是否让教练更容易理解？
5. 它是否能沉淀到论文或阶段汇报？

如果答案都是否，那就先不做。

## 8. 心态

这个工程确实大，但你不需要一次理解全部。

你每天只需要推进一个小闭环：

```text
今天让视频能登记。
明天让视频能抽帧。
后天让 baseline 跑起来。
再后天让失败样本能被标记。
```

大型项目不是靠一次性想明白做成的，而是靠每天把边界清楚的小模块做稳。
